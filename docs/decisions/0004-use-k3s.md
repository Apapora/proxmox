# 4. Use k3s for the Kubernetes cluster

Date: 2026-05-21
Status: Accepted

## Context

Need a Kubernetes distribution to run inside VMs provisioned by Terraform on
the single PVE host. Candidates considered: minikube, kind, MicroK8s, k0s,
k3s, kubeadm.

Hardware budget (64GB RAM, 16 cores) easily handles any of them. Decision
hinges on learning value, persistence, multi-node realism, and how much the
skills transfer.

## Decision

Use k3s.

Why:

- Real multi-VM cluster — SSH into named nodes, drain/cordon, watch pod
  rescheduling. Matches production mental model. minikube/kind hide this.
- Persistent — survives reboots. Not a tear-down-on-exit dev tool.
- Production-grade — CNCF Sandbox, used in real prod (edge, IoT, homelabs).
  Skills transfer to enterprise k8s clusters.
- Right-sized for the hardware. kubeadm would also work but adds steps that
  teach "how to do kubeadm" rather than "how Kubernetes works".
- Friendly defaults (Traefik ingress, local-path storage, servicelb, flannel
  CNI) that can be ripped out one at a time as learning advances.

## Consequences

- Some k3s-specific defaults will be replaced later (MetalLB instead of
  servicelb, Cilium instead of flannel, Longhorn instead of local-path) —
  these swaps are explicit learning milestones, not workarounds.
- Cluster topology: 1 server (control plane + etcd embedded, also schedules
  workloads via untaint) + 2 agent nodes. Adjust later if HA control plane
  becomes a learning goal.
- If the k3s arc completes and a "raw kubeadm" experience is wanted, the
  Terraform + Ansible layers stay; only the k8s install role changes.
